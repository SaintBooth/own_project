FE-C01
Отсутствует дизайн-система и выбор UI-библиотеки
Critical
Вся документация не содержит ни слова о дизайн-токенах, цветовой палитре, типографике, сетке или компонентной библиотеке. Разработчик будет принимать эти решения в процессе, что неизбежно приведёт к несогласованному UI. Не определено: использовать ли shadcn/ui, Radix UI, Mantine или кастомные компоненты. Отсутствует: выбор шрифтовой пары, темновой/светлой темы, минимального набора дизайн-токенов (--color-primary, --radius, --spacing).
→ Рекомендация

Добавить раздел 12.6. Design System: выбрать shadcn/ui + Tailwind CSS (оптимально для Next.js 15 App Router), зафиксировать цветовую систему (brand, neutral, semantic), типографику (next/font с конкретными семействами), брейкпоинты и базовую тему.

design-system shadcn/ui tailwind tokens
FE-C02
Нет спецификации real-time доставки in-app уведомлений
Critical
Раздел 23 подробно описывает backend-доставку уведомлений (Celery, Email, Telegram), но полностью умалчивает о том, как in-app уведомления появляются в браузере в реальном времени. Есть три варианта с разными реализациями: Server-Sent Events, WebSocket (Django Channels), или polling. Документ даёт только endpoint GET /users/me/notifications/, но не говорит: клиент должен поллить? с каким интервалом? или есть push?
→ Рекомендация

Добавить 23.7. Доставка в браузер: явно выбрать один механизм. Для MVP — polling каждые 30 сек при открытом дашборде (простота). Для v2 — SSE через GET /api/v1/events/ (без Django Channels, через Nginx buffering). Зафиксировать badge-счётчик непрочитанных в Zustand store.

SSE websocket polling zustand
FE-C03
Раздел 19 (env vars) не содержит ни одной NEXT_PUBLIC_ переменной
Critical
В разделе 19 перечислены исключительно backend-переменные. Frontend-приложению Next.js нужны собственные публичные переменные. Без них разработчик не знает, как конфигурировать приложение. Как минимум отсутствуют: NEXT_PUBLIC_API_URL, NEXT_PUBLIC_CAPTCHA_SITE_KEY (для Turnstile/reCAPTCHA), NEXT_PUBLIC_YANDEX_CLIENT_ID (кнопка OAuth), NEXT_PUBLIC_YM_COUNTER_ID (Яндекс.Метрика), NEXT_PUBLIC_TELEGRAM_BOT_USERNAME (Login Widget).
→ Рекомендация

Добавить подраздел 19.2. Frontend ENV (NEXT_PUBLIC_*) с полным списком переменных окружения Next.js. Уточнить, какие переменные безопасно выставлять в браузер, а какие должны оставаться только на сервере (Server Components / route handlers).

env-vars next.js NEXT_PUBLIC config
FE-C04
Нет стратегии Error Boundaries и fallback UI
Critical
Документ описывает поведение API при ошибках (401 → refresh, 403, 422, 500), но не определяет пользовательский опыт при ошибках на стороне UI. Что видит покупатель, если Vault недоступен и контент не расшифровывается (503)? Что показывается при сетевой ошибке в каталоге? Нет указаний на error.tsx, not-found.tsx, global-error.tsx в Next.js App Router.
→ Рекомендация

Добавить 12.7. Error Handling UI: таблицу маппинга HTTP-ошибок → UI-состояний, обязательные error.tsx компоненты для каждой route group, not-found.tsx, global-error.tsx. Описать toast-нотификации (библиотека: sonner или react-hot-toast).

High

Блокирует конкретные фичи
FE-H01
Skeleton-экраны и loading states не специфицированы
High
Каталог работает на cursor pagination с network запросами, поиск — на pgvector (latency p95 <500ms). Ни слова о том, что видит пользователь во время загрузки. Без loading.tsx и скелетонов — каталог будет «прыгать» при загрузке (CLS). Это напрямую влияет на Core Web Vitals (CLS <0.1 — цель из раздела 17).
→ Рекомендация

Добавить 12.8. Loading States: указать loading.tsx для /catalog, /prompt/[slug], /library. Зафиксировать Suspense boundaries. Рекомендовать Skeleton UI (shadcn Skeleton или CSS shimmer) для карточек каталога.

loading.tsx Suspense CLS skeleton
FE-H02
Библиотека валидации форм не выбрана
High
Формы занимают значительную часть платформы: OTP вход, создание промпта, KYC, настройки продавца, фильтры каталога, отзывы. Backend использует Pydantic схемы (Django Ninja), но frontend-валидация не описана. Дублировать схемы вручную — ошибкоёмко. Не указан: react-hook-form, zod, интеграция с Pydantic-схемами через OpenAPI codegen.
→ Рекомендация

Зафиксировать: react-hook-form + zod. Добавить в CI шаг генерации TypeScript-типов из OpenAPI схемы Django Ninja через openapi-typescript — это устранит рассинхрон типов между backend и frontend на уровне CI.

react-hook-form zod openapi-typescript validation
FE-H03
KYC Onboarding UX: что видит продавец во время PENDING?
High
Бэкенд подробно описывает жизненный цикл KYC (PENDING → VERIFIED / REJECTED / CANCELLED), но UX-сторона страницы /seller/kyc не определена. Как долго ждёт продавец? Есть ли индикатор прогресса? Как он узнаёт о результате (только email, или UI обновляется)? Нет описания состояний: пустой, заполненный, ожидание, ошибка, успех — для KYC-формы.
→ Рекомендация

Добавить 12.9. KYC Onboarding States — state machine с 5 UI-состояниями: idle → submitted (spinner) → PENDING (polling каждые 10 сек) → VERIFIED (success, redirect to dashboard) → REJECTED (error с причиной + retry).

KYC UX state machine polling onboarding
FE-H04
Отображение расшифрованного контента промпта не специфицировано
High
Это ключевой экран продукта — страница, куда попадает покупатель после оплаты. API возвращает { "content": "string", "instruction": "string", "variables": [...] }. Но UX не описан: как отображать переменные (поле variables — JSONField)? Есть ли кнопка «Скопировать»? Как выглядит блок с инструкцией? Отображать ли форму подстановки переменных (TOPIC=...)?
→ Рекомендация

Добавить 12.10. Prompt Content View: структура страницы — instruction block + variables substitution form (если variables.length > 0) + content block (pre-formatted, copy button) + examples gallery. Копирование — через Clipboard API с toast-уведомлением.

content-view variables clipboard UX
FE-H05
Payment UX: redirect в Robokassa и страница результата
High
Раздел 11.3 упоминает SuccessURL=/payment/result?purchase_id={uuid}&status=success|fail, но страница /payment/result не упомянута в роутинге раздела 12.1. Что видит покупатель после возврата из Robokassa? Как обрабатывается статус fail (неоплата, отмена)? Нет описания промежуточного экрана «ожидания подтверждения» (webhook может прийти с задержкой).
→ Рекомендация

Добавить /payment/result/page.tsx в роутинг. Описать логику: при status=success — polling GET /payments/purchases/{id}/ до статуса SUCCESS (max 30 сек) → redirect в /library. При status=fail — страница с объяснением + кнопка «Повторить».

payment robokassa routing polling
FE-H06
UX загрузки файлов (presigned URL flow) не описан
High
Backend описывает двухшаговый upload: POST .../upload-url/ → presigned PUT → POST .../confirm/. Это нестандартный флоу. Фронтенд-разработчик должен понять: drag & drop или file input? Как показывать прогресс (XHR progress event на presigned PUT)? Что происходит при ошибке на шаге confirm (422)? Как показывать превью до и после загрузки?
→ Рекомендация

Добавить 12.11. File Upload UX: описать компонент DropZone → Upload Progress → Confirm call → Preview. Рекомендовать react-dropzone или shadcn FileUpload. Показать последовательность API-вызовов с состояниями UI.

file-upload presigned-url drag-drop progress
FE-H07
Аналитика продавца: библиотека для графиков не выбрана
High
Раздел 4.2 упоминает «дашборд аналитики: просмотры, продажи, конверсия», раздел 20.3 — бизнес-метрики. API endpoint GET /seller/analytics/ возвращает числа, но нет ни одного слова о визуализации: линейный или столбчатый график? date range picker? какая библиотека (Recharts, Tremor, Chart.js, Nivo)? Решение влияет на bundle size (Recharts ~300KB, Nivo ~600KB).
→ Рекомендация

Зафиксировать Recharts (самая лёгкая, хорошо работает с SSR). Описать набор виджетов: Revenue Line Chart (7/30/90 дней) + Sales Bar Chart + KPIs row (GMV, conversion, avg price). Date range picker — react-day-picker (уже есть в shadcn/ui).

recharts analytics charts bundle-size
FE-H08
Frontend CI: линтинг и тестирование не описаны
High
Раздел 18 (CI) описывает backend-проверки (pytest, Bandit, ruff, mypy), но для фронтенда — ноль. Не зафиксировано: ESLint конфигурация (next/core-web-vitals? airbnb?), TypeScript strict mode ("strict": true), unit-тесты (vitest или jest?), проверка размера бандла (@next/bundle-analyzer), prettier.
→ Рекомендация

Добавить в CI шаги: eslint --max-warnings 0, tsc --noEmit (TypeScript strict), vitest run, next build (проверка bundle). Зафиксировать целевой бюджет: JS bundle <300KB gzip для initial page load.

eslint typescript-strict vitest bundle-budget

Medium

Ухудшает качество продукта
FE-M01
Accessibility: нет WCAG целей и требований
Medium
Ни в разделе 12, ни в разделе 17 (SEO) нет упоминания о доступности. Для маркетплейса это риск: без явных требований разработчики не добавят aria-labels, keyboard navigation, focus management. Маркетплейс с финансовыми транзакциями должен поддерживать WCAG 2.1 AA минимум.
→ Рекомендация

Добавить 12.12. Accessibility: цель WCAG 2.1 AA, обязательные атрибуты для карточек каталога (role="article", aria-label), кнопок покупки (aria-busy), модальных окон (aria-modal). Добавить axe-core в CI для автопроверки.

FE-M02
Cookie consent UI не специфицирован
Medium
Раздел 2.2 требует: «Cookie-баннер: Яндекс.Метрика инициализируется только после клика Согласен». Это UI-компонент с persistence (localStorage), но его реализация нигде не описана. Использовать готовую библиотеку (react-cookie-consent) или кастомный баннер? Как хранить согласие (localStorage key, срок)? Как интегрировать с NEXT_PUBLIC_YM_COUNTER_ID?
→ Рекомендация

Описать компонент CookieConsent: хранение в localStorage['cookie_consent'] со значением accepted|rejected|null. Яндекс.Метрика подключается через next/script strategy="afterInteractive" только при accepted.

152-ФЗcookieya.metrika
FE-M03
ISR стратегия каталога не определена
Medium
Раздел 17 упоминает ISR для sitemap (revalidate 3600), но для страниц каталога и карточек промптов стратегия кеширования не описана. При SSR без кеша каждый запрос бьёт по Django + PostgreSQL — при 1000 RPS (нагрузочный тест из 15.5) это проблема. Не определено: revalidatePath при публикации нового промпта? ISR для /prompt/[slug]?
→ Рекомендация

Добавить таблицу кеш-стратегий: /catalog — ISR revalidate=60; /prompt/[slug] — ISR revalidate=300 + revalidatePath при смене статуса промпта; /seller/[username] — ISR revalidate=600.

FE-M04
next.config.ts: security headers и image domains не определены
Medium
next/image требует явного whitelist доменов для оптимизации. Не указан домен YOS (storage.yandexcloud.net) и CDN. Раздел 8.2 упоминает CSP, но конкретный Content-Security-Policy заголовок для Next.js не описан. Также не упомянуто: output: 'standalone' (нужен для Docker).
→ Рекомендация

Добавить раздел 12.13. next.config.ts с: images.remotePatterns для YOS + CDN, headers() с CSP/HSTS/X-Frame-Options, output: 'standalone' для Docker, experimental.typedRoutes: true.

next.configCSPdockersecurity
FE-M05
OG Image: стратегия генерации не описана
Medium
Раздел 17 упоминает og:image на карточках промпта («первый пример результата или дефолтная обложка»). Но не описано: что такое «дефолтная обложка» визуально? Как генерировать динамические OG-images для промптов без пользовательских примеров? Next.js 13+ поддерживает ImageResponse (Edge Runtime) для генерации OG-images из JSX.
→ Рекомендация

Описать opengraph-image.tsx через Next.js ImageResponse: брендовый шаблон с названием промпта, категорией, ценой и лого. Для промптов с примерами — использовать первый PromptOutputExample через CDN URL.

og:imageImageResponseSEOedge
FE-M06
Яндекс.Метрика: план аналитических событий отсутствует
Medium
Яндекс.Метрика упомянута как инструмент аналитики, но нет никакого плана событий (event tracking). Без этого нельзя измерять конверсию. Ключевые события для маркетплейса: prompt_view, add_to_favorites, payment_started, payment_success, kyc_submitted, search_query, filter_applied — ни одно не описано в документе.
→ Рекомендация

Добавить 17.x. Analytics Events: таблицу событий с ym(COUNTER_ID, 'reachGoal', 'goal_name', params). Критичные цели: payment_success, free_prompt_acquired, seller_kyc_submitted, semantic_search_used.

ya.metrikagoalsanalyticsconversion
FE-M07
Состояния Zustand stores: только auth store упомянут
Medium
В разделе 12.2 упоминается «глобальный auth store» в Zustand. Но для платформы с каталогом, фильтрами, уведомлениями и покупками нужны и другие stores. Не описана архитектура состояния: notifications store (badge counter, список), catalog filters store (URL sync?), cart/payment state. Без этого разработчики будут изобретать структуры самостоятельно.
→ Рекомендация

Добавить 12.14. State Management: перечислить stores — authStore, notificationsStore (unread count + items), catalogFiltersStore (синхронизация с URL через nuqs). Всё остальное — React Server Components или React Query.

Тёмная тема: выбор не зафиксирован
Low
Нет указаний на поддержку тёмной темы. Пользовательская аудитория маркетплейса AI-промптов ожидает тёмный режим как стандарт (2026). Не зафиксировано: поддерживать ли prefers-color-scheme, хранить ли выбор в localStorage, использовать ли next-themes.

FE-L03
Мобильная навигация не описана
Low
Раздел 17 говорит «Mobile-First», но нет описания мобильного навигационного паттерна. Для платформы с ролевыми кабинетами это нетривиально: hamburger menu + drawer? Bottom navigation bar? Как переключаться между ролями (buyer / seller) на мобильном?
